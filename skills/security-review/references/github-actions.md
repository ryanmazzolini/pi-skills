# GitHub Actions Security Review

Use this reference for `.github/workflows/*.yml`, reusable workflows, composite/local actions, root `action.yml`, and scripts/config loaded by workflows.

## Trust Map

For changed workflow code, build a quick map before reporting:

- **Trigger and actor**: fork PR, issue/comment, manual dispatch, reusable caller, schedule, release, push, or privileged follow-up workflow.
- **Controlled data**: PR refs, branch names, titles/bodies, comments, labels, file lists, workflow inputs, action outputs, artifacts, caches, and local action/script contents.
- **Privilege point**: secrets, PATs, deploy keys, package/release authority, OIDC `id-token: write`, write-scoped `GITHUB_TOKEN`, protected environments, or self-hosted runners.
- **Execution path**: checkout refs, local actions, shell/script steps, package manager lifecycle hooks, reusable workflows, downloaded artifacts, and generated caches.

A finding needs untrusted influence connected to a privilege point or sensitive side effect.

## Boundary Checks

### PR and checkout trust

- `pull_request_target` and privileged `workflow_run` are dangerous when they checkout, build, test, or execute PR-controlled refs before privileges are removed.
- Local actions, Makefiles, package scripts, and config files are code. If they come from an untrusted checkout, they can use the job’s token, secrets, runner, and network.
- Metadata-only target workflows are usually fine when they avoid executing PR-controlled data as code.

### Text-to-code injection

- Treat PR titles/bodies, comments, branch names, labels, changed filenames, and free-form workflow inputs as untrusted text.
- Dangerous sinks include shell `run:`, `bash -c`, `node -e`, `python -c`, `github-script` JavaScript bodies, workflow command files, and composite action shell steps.
- Passing text through `env:` is safer only if later shell/script usage quotes and validates it.

### Artifacts, caches, and promotion

- Privileged jobs should not execute or blindly trust artifacts/caches produced by untrusted PR jobs.
- Upload paths should be narrow. Workspace or home-directory uploads after checkout/login/setup steps can leak credentials or generated config.
- Package/release/deploy jobs need immutable artifact provenance and should not use lower-privileged inputs to choose what gets published.

### Supply chain and runner boundaries

- Mutable third-party action refs matter most in jobs with secrets, OIDC, write tokens, release/package/deploy powers, or signing authority.
- Self-hosted runners should not run untrusted PR/comment/manual-input code unless the runner is disposable and isolated for that trust level.
- Coding-agent workflows should avoid privileged runs on PR-controlled checkouts or instruction files such as `AGENTS.md`, `CLAUDE.md`, or Copilot instructions.

## Calibration Notes

- Broad `permissions:` alone is not a finding. Tie it to untrusted execution, credential exposure, artifact trust, or a privileged side effect.
- Plain `pull_request` from forks usually lacks base secrets and has restricted token privileges. Look for downstream privileged consumers before escalating.
- Expressions inside `if:` or ordinary `with:` values are not automatically code execution; inspect how the receiving action or later script interprets the value.
- First-party `actions/*` version tags are normally acceptable by themselves. Third-party pinning concerns should be tied to meaningful job privilege.
- `persist-credentials: false` protects checkout credentials only; it does not protect unrelated PATs, cloud credentials, OIDC, or registry tokens.

## Examples

### Report: privileged target workflow runs fork code

```yaml
on: pull_request_target
permissions:
  contents: write
  packages: write
jobs:
  package:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          repository: ${{ github.event.pull_request.head.repo.full_name }}
          ref: ${{ github.head_ref }}
      - run: npm ci
      - run: npm run publish-snapshot
```

Fork-controlled package scripts run with trusted-repository publish privileges.

### Report: comment text reaches shell

```yaml
on: issue_comment
jobs:
  chatops:
    steps:
      - run: |
          ./scripts/deploy-preview ${{ github.event.comment.body }}
```

Comment text is expanded into a shell command in a workflow reachable by lower-privileged users.

### Report: broad artifact upload after publish setup

```yaml
steps:
  - uses: actions/checkout@v4
  - run: npm publish --provenance
  - uses: actions/upload-artifact@v4
    with:
      path: ${{ github.workspace }}
```

The uploaded workspace can include checkout, package-manager, or release credentials generated by earlier steps. Upload explicit build output paths instead.

### Do not report: metadata-only target workflow

```yaml
on: pull_request_target
permissions:
  issues: write
jobs:
  acknowledge:
    steps:
      - env:
          PR_NUMBER: ${{ github.event.pull_request.number }}
        run: gh issue comment "$PR_NUMBER" --body "Thanks, a maintainer will review this."
```

If the workflow does not checkout or execute PR-controlled code/data and uses only trusted metadata safely, this is not a privileged PR code execution finding.
